# Chat Modes & Pre-flight Decomposition UI — Design Spec

_Created: 2026-03-21_

---

## Overview

Two features that work together: a multi-mode chat interface and a pre-flight decomposition UI where the orchestrator presents scenario plans before dispatching agents.

---

## 1. Chat Modes

The prompt input supports three modes. Each mode shows buttons on the drag handle for transitioning to the other available modes.

### 1.1 Minimized (default)

- Current behavior: floating prompt input bar at bottom of sandbox area
- Drag handle shows **maximize** (float) and **dock** buttons
- This is what users see on session load

### 1.2 Float Maximized

- Larger floating panel overlaying the sandbox area
- Shows full message history, plan cards, and input field
- Drag handle shows **dock** and **minimize** buttons
- **Auto-minimizes** after agent dispatch or when conversation reaches a natural pause point (agents dispatched, question answered)

### 1.3 Docked Sidebar

- Fixed panel to the left of the agents panel
- Persistent — does NOT auto-minimize after dispatch
- Shows **float** button only (one transition: docked → float maximized)
- Layout becomes: `[Avatars] [Chat (docked)] [Agents Panel] [Sandbox]`

### 1.4 Mode Transitions

```
Minimized       → maximize → Float Maximized
                → dock     → Docked Sidebar

Float Maximized → dock     → Docked Sidebar
                → minimize → Minimized

Docked Sidebar  → float    → Float Maximized
```

### 1.5 Auto-behaviors

- When the orchestrator returns a pre-flight plan and chat is minimized, chat **auto-maximizes** to float mode to show the plan cards
- After the user clicks "Run selected" in float mode, chat **auto-minimizes** since the action is complete
- In docked mode, no auto-minimize — the panel stays open as a persistent workspace element

### 1.6 Auto-minimize Triggers (float mode only)

Auto-minimize fires in float mode when:

1. User clicks "Run N selected" and dispatch succeeds
2. Orchestrator returns a non-plan response (simple text answer) and 3 seconds elapse with no further typing

Auto-minimize does NOT fire when:

- An error occurs during dispatch (user needs to see the error)
- The orchestrator asks a clarifying question (conversation continues)

## 2. Pre-flight Decomposition UI

### 2.1 Flow

1. User types a prompt in any chat mode and sends to the orchestrator
2. If chat is minimized, it auto-maximizes to float mode
3. Orchestrator analyzes the request + selected frames + context
4. Orchestrator returns a structured plan as a special message type in the chat
5. Plan renders as interactive scenario cards with checkboxes
6. User checks/unchecks scenarios and optionally adds custom ones
7. User clicks "Run N selected" to dispatch
8. Each checked scenario spawns an agent (appears in agents panel)
9. If floating → auto-minimize. If docked → stays open.

### 2.2 Plan Card UI

Plan cards appear inline in the chat as a special message component (not a modal or overlay).

```
┌─────────────────────────────────────┐
│  We identified 4 scenarios:         │
│                                     │
│  [x] Empty cart state               │
│      No items, show empty CTA       │
│                                     │
│  [x] Payment failure                │
│      Card declined mid-checkout     │
│                                     │
│  [ ] Guest checkout                 │
│      No account, email-only flow    │
│                                     │
│  [x] High-privilege admin view      │
│      Admin sees all orders + refund │
│                                     │
│  + Add scenario...                  │
│                                     │
│              [Run 3 selected]       │
└─────────────────────────────────────┘
```

### 2.3 Plan Card Structure

Each scenario card contains:

- **Checkbox** — toggle inclusion in the dispatch batch
- **Scenario name** — short title (generated by orchestrator)
- **Description** — one-line summary of what the scenario covers

### 2.4 Custom Scenario Addition

- "Add scenario..." input at the bottom of the plan cards
- User types a name and optional description
- Added scenario is checked by default
- No limit on custom additions in v1

### 2.5 "Run N selected" Button

- Label dynamically reflects count of checked scenarios: "Run 2 selected", "Run all 4"
- Disabled when zero scenarios are checked
- On click: dispatches checked scenarios to the orchestrator for agent spawning

### 2.6 Plan Data Shape

Uses the existing types from `packages/opendesign/src/agent/orchestrator.ts`:

```typescript
// Already defined — do not duplicate
import { PreFlightPlan, ScenarioPlan } from "@opencode-ai/opendesign/agent"

// ScenarioPlan: { scenario: string, description: string, frames?: string[], selected: boolean }
// PreFlightPlan: { scenarios: ScenarioPlan[], summary?: string }
```

The orchestrator returns a JSON block in its assistant message text. The client uses `parsePreFlightPlan(text)` from the same module to extract it. User interactions (check/uncheck, add custom) mutate a local copy of `scenarios[].selected`. On "Run selected", the filtered subset is sent back.

### 2.7 Plan Message Detection

The pre-flight plan is NOT a special message type. It is a regular assistant message whose text content contains a JSON block. Detection flow:

1. Client receives an assistant message via SSE
2. Client calls `parsePreFlightPlan(message.content)` on each assistant message
3. If it returns a `PreFlightPlan`, render the plan card UI instead of plain markdown
4. If it returns `null`, render as a normal message

This avoids adding new message types to the session model.

### 2.8 Dispatch API

When the user clicks "Run N selected":

1. Client filters `scenarios.filter(s => s.selected)` from the local plan state
2. Client sends a new user message to the session with the selected scenarios serialized as JSON:

   ````
   Dispatch these scenarios:
   ```json
   { "scenarios": [...selected], "summary": "..." }
   ````

   ```

   ```

3. The orchestrator agent receives this as a follow-up message and spawns scenario sub-agents
4. Each spawned agent appears in the agents panel via the existing SSE agent state events

No new API endpoints are needed — dispatch flows through the existing session message API.

### 2.9 Plan Card States

Plan cards have three states:

**Active** — Initial state when plan arrives. Checkboxes are interactive, "Add scenario" and "Run N selected" are available.

**Dispatched** — After user clicks "Run N selected". Checkboxes become read-only. Button text changes to "Dispatched N scenarios" (disabled). Plan card remains visible in chat history for reference.

**Stale** — If the user sends a new prompt that triggers a new plan, the previous plan card becomes stale. Checkboxes read-only, button hidden. A subtle dimming or opacity reduction indicates it is no longer actionable.

### 2.10 Error Handling

**Orchestrator fails to return valid plan:** If `parsePreFlightPlan` returns `null`, the message renders as normal markdown. No plan cards shown. User can rephrase and try again.

**Dispatch fails (network/server error):** Plan card stays in Active state. An inline error message appears below the "Run N selected" button: "Failed to dispatch — try again". Button remains clickable for retry.

**Partial agent spawn failure:** If some agents fail to spawn, the agents panel shows them with an error state. Plan card still transitions to Dispatched — individual agent errors are handled in the agents panel, not the plan card.

## 4. Scope Boundaries

### In scope (this spec)

- Three chat modes with toggle buttons on drag handle
- Auto-maximize on plan arrival, auto-minimize on dispatch (float only)
- Pre-flight plan cards inline in chat
- Check/uncheck scenarios
- Add custom scenario
- "Run N selected" dispatch button

### Out of scope (later)

- "What if" question cards from agents during work
- Agent-specific follow-up prompts in chat
- Drag-to-dock gesture
- Keyboard shortcuts for mode switching
- Chat history persistence across sessions
